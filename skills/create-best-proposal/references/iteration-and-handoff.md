# 반복 제작·재검증·세션 인계

기존 단계 A–E와 제출 게이트를 유지하면서, 새 디자인을 시험하거나 긴 제작을 이어 갈 때 읽는다.
일반적인 짧은 검토에는 별도 기록 파일이나 추가 승인 단계를 만들지 않는다.

## 1. 불확실한 디자인은 대표 장표로 먼저 확인

새 브랜드·템플릿·폰트 또는 아직 검증하지 않은 레이아웃을 도입하면 전체 본문을 채우기 전에
대표 장표 3장 안팎으로 확인한다. 분량은 고정 의무가 아니라 위험을 드러내는 데 필요한 만큼이다.
예: 리드문과 출처가 있는 본문, 가장 밀도 높은 표·조견표, 구성도·절차 중 실제로 쓸 유형.
기존 승인 양식의 단순 내용 수정에는 생략할 수 있다.
긴 REQ-ID 목록과 간트 마일스톤도 포함해 하단 줄바꿈·페이지 번호 간격·막대 위 글자 대비를 확인한다.

- 최종본과 같은 `meta.output_profile`·`meta.output_spec`·팔레트·템플릿을 사용한다.
- 기존 `build_deck.py --strict`와 `deck_check.py --stage draft --render`로 생성·검사한다.
  `--png-dir`·`--emit-render`에는 파일럿 전용 출력 위치를 지정해 최종 증거를 덮어쓰지 않는다.
- PNG에서 잘림·표 넘침·겹침·폰트 대체·읽기 거리를 확인한다. 고칠 점이 없거나
  사용자가 디자인 결정을 요청한 경우의 결정이 확보되면 전체 제작으로 진행한다.
- 렌더 도구가 없으면 시각 검증은 `NOT INSPECTED`로 남긴다. 파일럿 통과는 전체 덱의
  검수·육안 승인·제출 판정을 의미하지 않는다. 최종본은 기존 Phase D·E를 모두 거친다.

## 2. 수정 범위에 맞춰 검사를 다시 실행

작업 단위마다 대상 REQ-ID·평가 항목, 수정할 파일·장표, 완료 기준을 먼저 정한다.
`작성 → 해당 검사 → 지적 수정 → 재검사` 순으로 진행하고 실제 결과를 확인한다.
검사 명령·종료 코드·출력 경로와 사용한 입력/산출물 버전 또는 해시를 함께 남긴다.

| 바뀐 것 | 다시 확인할 것 |
|---|---|
| RFP·수정공고·Q&A·평가표 | 단계 A 출처·참여 판단과 stale sweep → 영향 REQ-ID·평가 링크·본문·조견표 |
| 금액·기간·수량·SLA | 수치 원장과 관련 본문/PT/별첨 동시 수정 → 검산·`check_numbers.py`·통합 게이트 |
| 내용·폰트·표·레이아웃·템플릿 | PPTX 재생성 → 배치·렌더 검사 → 변경된 장표와 인접/분할 장표 확인 |
| 본문 누락·근거/효과 혼동 | RFP 하위 조건 → 실제 PPTX 응답 대조 → 문장·조견표 동시 수정 → 새 렌더에서 재확인 |
| 최종 문서·첨부 파일 | 새 파일 해시 → 해당 파일에 대한 검토·승인 기록 → audit 재생성 → `unified_gate.py --doc ... --bundle ... --stage submission` |

모든 최종 장표에 대한 육안 검토와 기존 승인 조건은 그대로 적용한다. 이전 승인을 새 해시에
그대로 복사하거나 `visual_review_approved`를 자동으로 true로 바꾸지 않는다. 수정된 실제 파일에
대해 검토를 수행하고, 최종 render/package/첨부 해시가 같은 제출 후보를 가리키는지 확인한다.
`--audit-only` 성공은 수정된 파일의 제출 검증이 아니다.

렌더 실패는 재시도 전에 로그·도구·폰트·입력 오류부터 구분한다. 같은 원인으로 수정·재검증이
3회 실패하면 자동 반복을 멈추고 가설·시도·실패 증거·blocker·필요 입력을 보고한다.
미설치 도구, 부재한 자격 증빙, 승인 대기는 반복 실행으로 해결한 것으로 간주하지 않는다.
차단을 없애려고 stage를 낮추거나 검사·요구·근거·승인 필드를 제거하지 않는다.

## 3. 독립 검토와 도구 부재 처리

긴 제안이나 고위험 약속의 Red 검토에서는 가능한 경우 작성자와 다른 검토자 또는 독립
컨텍스트를 사용한다. 검토 입력은 최신 RFP·평가표·원장과 실제 제출 후보, 대상 장표 및
검사 결과로 제한하고 작성자의 자기평가를 정답으로 주지 않는다.
검토 결과에는 심각도, REQ-ID/장표/근거 위치, 필요한 최소 조치를 남긴다.
위임이 불가능하면 그 한계를 명시하고 직접 검토하되 독립 검토가 끝났다고 쓰지 않는다.
에이전트 의견은 기계 검사나 요구되는 사람의 시각·제출 승인을 대체하지 않는다.

## 4. 장기 작업만 상태와 교훈을 보존

여러 세션에 걸치는 경우 사용자 작업 폴더의 기존 진행 기록을 우선 사용한다.
설치된 스킬·플러그인이나 공개 저장소에는 고객 자료를 기록하지 않는다.
마일스톤 완료, 중요한 결정, blocker, 인계 시에만 갱신한다.

인계 기록에는 다음을 남긴다.

- 현재 요청 경로(Full/Pink/Red/Gold 등)·Phase, 마지막으로 검증된 작업 단위, 다음 최소 작업
- RFP·수정공고의 우선순위와 버전, 원장·slides.json·meta·audit·제출 후보의 위치와 버전/해시
- 실제 실행한 명령·종료 코드·결과 위치, 실패·미검사 항목과 남은 Critical/Major
- 미결정 사항·blocker·필요 입력/담당자, 승인 범위와 검토 대상 파일 해시

재개 시 기록을 사실로 추정하지 말고 실제 파일·해시·최신 수정공고와 대조한다.
기록 후 파일이 바뀌었거나 검사 증거를 찾을 수 없으면 영향 검사를 다시 수행한다.
컨텍스트 사용률 같은 고정 수치를 전제하지 않는다. 요구나 판단이 흐려지면 이 기록으로 인계한다.

반복된 실패에서 확인한 원인·해결·재검증 결과만 짧게 축적하고, 다음 유사 작업에서 관련 항목만
읽는다. 한 고객의 예외·가설·실패한 해결책을 보편 규칙으로 올리지 않는다.
이 기록은 프로젝트 운영 자료이며 audit JSON의 새 승인 필드나 자동 통과 근거가 아니다.
