# 기술 서술 깊이 — 작성 전 6문

키워드 나열형 기술 장표("고가용성 구성", "자동화 적용", "보안 강화")를 막는 내부 검토 절차다.
6문의 답은 작성 메모이며 장표에 그대로 옮기지 않는다. 장표는 §3 구조로 압축한다.

## 1. 적용 대상

- 유형 C 기술답변서의 핵심 항목
- 아키텍처, 마이그레이션, HA/DR, 보안, 성능, SLA, 데이터, 운영 자동화
- 평가표 고배점 기술 항목에 대응하는 장표

일반 소개·조직·일정 장표에는 적용하지 않는다.

## 2. 6문

| # | 질문 | 답이 부족한 신호 |
|---|---|---|
| 1 | 무엇을 해결하는가 — 어느 요구·지표·제약에 대응하는가 | REQ-ID 없음, 문제 서술 없이 기술명부터 시작 |
| 2 | 왜 이 방식인가 — 검토한 대안과 선택 이유 | "업계 표준", "검증된 기술", "안정적"만 있음 |
| 3 | 어떻게 동작하는가 — 구성요소·데이터 흐름·전환 순서 | 구성도에 상자만 있고 흐름·프로토콜·순서 없음 |
| 4 | 어떻게 구축·운영하는가 — 설정·배포·모니터링·변경 절차 | 운영 주체와 절차가 없음 |
| 5 | 어떻게 검증하는가 — 시험 방법·지표·합격 기준 | "테스트 수행"만 있고 기준 없음 |
| 6 | 실패하면 어떻게 되는가 — 감지·완화·복구·수동 개입 경계 | 장애 시나리오 부재, "자동 복구"만 있음 |

자기 점검: 수식어를 모두 지워도 구성요소·메커니즘·수치·절차가 남는가. 남는 것이 없으면
다시 쓴다.

## 3. 장표 압축 구조

```
리드문     결론 (1문 + 2문 요약)
본문 도식  메커니즘 (3문, 4문 핵심)
본문 표    검증·증거 (5문: 시험 기준·결과·출처)
캡션       위험·경계 (6문 요약 + 적용 범위)
```

한 장에 다 들어가지 않으면 도식 장과 검증 장으로 나누고, 두 장의 리드문이 이어지게 쓴다.

## 4. 범위·근거가 필요한 표현

무중단, zero data loss, 100% 자동복구, 완벽, 유일, 최고, 압도적, 완전 자동화 같은 표현의
금지 목록과 대체 패턴은 `../create-proposal-document/references/writing-style.md` §2가 기준이다.
이 문서는 사전을 따로 두지 않는다.

기술 장표에서 추가로 지키는 것:

- 가용성·복구 목표는 **목표값 + 측정 조건 + 전제**로 쓴다(예: RTO 목표와 전환 시험 조건).
- 성능 수치는 시험 환경·부하 조건·출처를 같은 장에 둔다.
- 자동화 범위는 자동 구간과 사람 승인 구간을 나눠 적는다.

근거가 없으면 기존 정책을 따른다: `[NEEDS INPUT: owner — 항목]` 또는 `[unverified]`.

## 5. 예시 (구조만)

BAD 리드문: "고가용성 아키텍처로 안정적인 서비스를 제공합니다."

BETTER 리드문: "관리 노드 3중화와 스토리지 복제로 단일 장애점을 제거하고,
전환 시험으로 목표 복구시간 충족 여부를 검수 단계에서 확인합니다."

BETTER 캡션: "적용 범위: 운영계 클러스터. 재해복구 사이트 전환은 별도 절차(수동 승인) — REQ-ID"
